# `@deepseek-ai/dsh-blue-interaction`

English | [中文](README.zh.md)

Blue terminal UI interaction layer over [`dsh-blue-core`](../../blue/core/README.md): the bottom input editor with slash-command dispatch, the built-in `/quit`, `/resume`, `/new`, `/fork`, `/sessions`, `/help`, and `/theme` commands, the `ctx.userQuestions` overlay provider (one tabbed questionnaire per request), and the interactive four-choice `approval/request` answerer. The package imports no pi-tui: the main editor is the pi-tui Editor behind `ctx.blueComponents.createEditor` (multi-line, history, kill-ring, undo, and paste markers built in), single-select lists come from `ctx.blueComponents.createSelectList`, and `BlueSelect` survives only as the package-internal multi-select list (pi-tui ships no multi-select). `BluePanel` is the package's sole public component export; overlays resolve keys through `ctx.blueKeymap` and style through `ctx.blueTheme`.

## Plugins

The single entry plugin `blue-interaction` mounts five sub-plugins; every registration is effect-bound, so unloading the fiber reverts every contribution (HMR-safe: the provider/command/key registrations disappear with the fiber).

- **`blue-interaction-keys`** — registers the shared key-action batch (`blue.interaction.submit/cancel/move-up/move-down/toggle`) on `ctx.blueKeymap` as one validated unit, plus the editor-context actions `blue.interaction.interrupt` (Ctrl-C) and `blue.interaction.steer` (Ctrl-S). The latter two carry no handler — they stay contextual and are resolved by the main editor's `onKey` hook, never by the global dispatcher, so they cannot steal a key from an overlay's `escape=cancel` route. The multi-select `BlueSelect` resolves keys against these actions and generates footer hints with `getKeys`; text-editing keys are owned by the pi-tui Editor itself.
- **`blue-input`** — mounts the focused bottom editor: the pi-tui Editor from `ctx.blueComponents.createEditor({ paddingX: 4 })` with the `>` prompt symbol set at mount (the padding and symbol feed the core adapter's rounded-box chrome), with the hint line as a separate `HintLine` component pinned below. The hint line carries three tiers: one-shot notices and slash-command discovery in `muted`, and beneath them the persistent key-affordance row in `textMuted` (`src/hint-content.ts` — idle fragments like `! bash · / commands · @ files · ctrl+s steer · ctrl+c exit` and running fragments `escape interrupt · ctrl+s steer`; key labels come from a `blueKeymap.getKeys` whitelist, `! bash`/`@ files` appear only while the `blue-editor-plus` presence mark is set, `ctrl+v paste image` only while its keymap action is registered), recomposed at render time so later plugin loads flip the row without re-wiring. Slash-prefixed input recolors the editor frame `primary` through `setBorderColor`; any other text restores the neutral border. Submit parses the line with `parseCommand`: a slash command dispatches through `ctx.commands.execute` (never reaching the model; success/error text flashes in the hint line), anything else becomes a `createUserMessage({ source: { kind: 'user' } })` follow-up on the current agent — queued by the harness inbox when the agent is running. The `onSubmit` callback argument already carries the paste-expanded, trimmed text. Slash-prefixed input shows up to three matching commands from `ctx.commands.list` as a discovery hint. The mounted editor and its submit router are published through a package-local shared ref so `blue-editor-plus` can layer input modes and autocomplete over the same component. The editor's `onKey` pre-dispatch hook resolves the editor-context key chain: Escape lets a showing autocomplete popup keep the key, then clears the draft, then interrupts a running agent; Ctrl-C clears the draft, then interrupts a running agent, and a second press within 1 s exits through the launcher-owned `appExit(0)` (a single press flashes the double-press hint in the hint line); Ctrl-S steers a non-empty draft into the current turn and clears the buffer. The unsubmitted draft and input mode are mirrored into a module-level stash (`src/draft-stash.ts`), so the theme-swap reload that rebuilds this fiber restores both into the fresh editor; submit and steer clear the stash.
- **`blue-commands`** — registers `/quit` (requests exit through the launcher-owned `ctx.appExit`; an error result when the launcher provided none), `/resume <session-id>` (emits `blue/request-resume`; the app layer performs the actual resume), `/new` (emits `blue/request-new`), `/fork` (emits `blue/request-fork`; an error result while the current agent is not idle), `/sessions` (lists persisted sessions newest-first from `sessionPersistence.list` in a picker overlay — the live session is marked and not selectable, picking another emits `blue/request-resume`, and the outcome flashes through the shared editor's `notice` seam), `/help` (a two-section overlay of the registered commands from `ctx.commands.list` and the key bindings from `ctx.blueKeymap.list()`; Escape, Enter, or `q` closes it), and `/theme` (swaps the live theme provider: `/theme` lists the known themes, marking the current one; `/theme dark|light|auto` switches to a built-in palette; `/theme custom <path> [dark|light]` mounts a file-backed palette; the switch disposes the current provider's fibers through `ctx.registry.delete` and mounts the replacement, and a failed mount restores the built-in dark palette). Only `commands` is injected: injecting `blueTheme` would make this fiber a theme dependent, and `/theme` would dispose its own handler's fiber mid-swap — every Blue display service is resolved lazily through `ctx.get` inside the handlers.
- **`blue-questions`** — registers the single `ctx.userQuestions` provider. The whole request — however many questions it carries — opens as one modal overlay (80%/60%) hosting the tabbed `Questionnaire` component (`src/questionnaire.ts`): a tab row (the question's `header` or `Q{i+1}`, the current tab accented, answered ones check-marked), Tab/Shift-Tab moving between questions, Up/Down + Enter for single-select, Space + Enter for multi-select, a fixed trailing `Other` pseudo-row opening an inline editor whose text becomes the answer's `custom`, and the editor alone for an optionless question; the request resolves once every question is answered. Escape rejects with `ASK_DISMISSED`; an aborted request signal closes the overlay and rejects with `ASK_ABORTED`. A `plan-review` intent is still not consumed.
- **`blue-approval`** — answers the `approval/request` waterfall for the agent currently attached to the UI with a modal four-choice overlay: `1` Allow once, `2` Allow {tool} for this session, `3` Reject, `4` Reject with feedback — navigated with Up/Down + Enter or direct-selected with the digit keys; Escape settles `'rejected'`, an aborted signal settles `'cancelled'`. Choice 2 records the tool in a module-level `WeakMap<Agent, Set<string>>`, and a later request for the same agent and tool skips the prompt entirely, returning `'allowed-once'`; choice 4 swaps the menu for an inline reason editor whose submission settles `'rejected'` and steers the agent with `createUserMessage('User rejected …: …')`. Concurrent prompts serialize on a module-level FIFO queue (an explicit array plus an active flag) so only one overlay is visible at a time — an idle queue starts its prompt synchronously, keeping the waterfall's synchronous visibility. Requests for any other agent, or arriving before a session attaches, delegate with `next()` — returning without `next()` short-circuits the waterfall.

The **`./editor-plus`** subpath plugin (`blue-editor-plus`) is the optional enhancement layer over the shared editor: the entry plugin does not mount it — a host patch opts in by adding the row. It attaches and re-attaches through the `'blue/input-editor-changed'` event, preserving the handlers `blue-input` installed.

- **`!` bash mode** — a buffer holding exactly `!` switches to bash mode without the `!` entering the buffer. The mode cue is the S11 triple: the `!` prompt symbol, the ` ! shell mode ` border label, and the `colors.shellMode` frame hue — re-asserted on every change while the mode is active, so a leading `/` (a path separator here) cannot drag the frame back to the slash-context blue. Every bash submission falls back to prompt mode first, restoring the `>` symbol and neutral border. Commands run through the package's own `child_process` executor (combined output capped at 200 lines and 64 KB) and echo into the scroll region as a `ShellEchoComponent` — deliberately not part of the session transcript. The input mode is mirrored into the draft stash, so a theme-swap reload rebuilds bash (triple included) around the restored draft.
- **Dispatching autocomplete** — one `BlueAutocompleteProvider` serving slash-command completion (prefix match over `ctx.commands.list`) and `@` file completion (`fd` first, an fs scan as fallback, capped at 200 candidates), installed through `BlueEditor.setAutocompleteProvider`.
- **Shared history** — prompt and bash submissions share the pi-tui Editor's internal history; the component exposes no per-mode filtering.

The **`./pane-queue`** subpath plugin (`blue-pane-queue`, inject `['blueScreen', 'blueTheme', 'blueKeymap']`) is the queued-message pane: a bottom-pinned component listing the attached agent's queued inbox messages — one muted `queued ↑ turn:|step:` row each, refreshed off the `agent/inbox/inserted|claimed|discarded` events filtered to that agent, zero rows while the inbox is empty. It also registers the keyless contextual action `blue.queue.recall`, whose presence in `ctx.blueKeymap.list()` gates the recall in `blue-input`: an Up press with an empty editor buffer removes the most recently queued message (the last `nextStep` entry wins over `nextTurn`, steering being the fresher intent) and makes its text the draft. The action binds no keys because `up` is already claimed by `blue.interaction.move-up` and the keymap rejects duplicate claims — the recall matches through the existing move-up binding; without this plugin the baseline leaves Up to the editor's history navigation.

The **`./attachments`** subpath plugin (`blue-attachments`, inject `['blueComponents']`) provides the harness `attachments` `AttachmentStore`: a `FilesystemAttachmentStore` with magic-byte sniffing (the shared sniffer export), a media-type whitelist plus caps (10 MB/image, 8 images/message, 30 MB/message, 16M pixels), storing files under `DSH_BLUE_ATTACHMENT_DIR ?? $DSH_HOME/attachments ?? ~/.dsh/attachments` as `<uuid>.<ext>`; `AttachmentError` codes follow dsh-attachment's taxonomy.

The **`./paste-image`** subpath plugin (`blue-paste-image`, inject `['attachments', 'blueKeymap']`) registers the contextual ctrl+v action `blue.image.paste`, resolved in a wrapper on the shared editor's `onKey` chain. The clipboard is read through an injectable reader defaulting to wl-paste → xclip probes (3 s timeout); the image is saved through `ctx.attachments` and an `[image #N]` marker is inserted at the cursor (`BlueEditor.insertText`; the module-level marker map survives theme-swap reloads). The submit transformer below splits markers into ImageBlocks; failures flash a notice, and completions arriving after the plugin unloads no-op.

## Submit-transformer seam

The shared-editor module (`src/editor-instance.ts`) exposes `registerSubmitTransformer(fn): disposer` and `applySubmitTransformers(text)`, which concatenates the registered contributions in registration order; an empty result keeps the historical single text block. Both the follow-up and steer paths build their message content through it — `blue-paste-image` uses it to split `[image #N]` markers into image blocks.

## The `blueSession` contract

The current agent is read with `ctx.get('blueSession')` (never `inject`) because the app plugin may activate after this one. `BlueSessionRef` and the `blue/request-resume` event are owned and declared by `@deepseek-ai/dsh-blue-app`; this package consumes them through type-only imports.

## Model Experience

None, as the interaction layer renders prompts and overlays to the user; the approval and user-question seams own any model-visible effect of the answers collected here.

#### KV Cache effect

None; the package adds nothing to any model request prefix.

## Known Limitations and Deferred Work

- **No per-mode history** — prompt and bash submissions share the pi-tui Editor's internal history; the component exposes no per-mode filtering.
- **Autocomplete scope** — completion covers slash-command names and `@` file paths; argument completion is deferred.
